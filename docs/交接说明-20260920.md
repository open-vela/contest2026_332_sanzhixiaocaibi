## 2. 双固件架构（务必先理解这一点）

一块 ESP32-P4，**同一时刻只能跑一个固件**，而且两者烧录地址重叠：

| 固件 | 地址 | 屏 | 摄像头 | 网络 | GPIO 断闸 | NSH |
|---|---|---|---|---|---|---|
| **openvela** | `0x2000` 单文件 | ✗ | ✗ | ✗ | ✓ | ✓ |
| **ESP-IDF** | `0x2000`/`0x10000`/`0x20000`/`0x920000` | ✓ | ✓ | ✓ | demo mode 下 ✗ | — |

openvela 的镜像（248KB）会盖掉 ESP-IDF 的 bootloader、分区表和 app 头部，
**互相覆盖，切换必须重烧**。

openvela 侧**没有** MIPI-CSI/DSI/LCD 驱动，也**没有**网络栈：

- `arch/risc-v/src/common/espressif/` 下 79 个文件，无任何 camera/display 相关
- `ESPRESSIF_WIFI` 的 Kconfig 是 `depends on ESPRESSIF_ESP32C3 || ESPRESSIF_ESP32C6`，**P4 不在列表**
- 树里没有 esp-hosted host 驱动
- `CONFIG_NET` 一条都没开

这不是配置问题，是上游能力空白。**已查证并写进技术报告，不要再去试图打开。**

## 3. openvela 侧：做完了什么、坏在哪

### 3.1 已完成并有实证

**GPIO 字符设备驱动适配**（真机验证通过）：

```
GPIO selftest: /dev/gpio0 OK  read=0  ioctl=0     GPIO21 三相断闸 SSR
GPIO selftest: /dev/gpio1 OK  read=0  ioctl=0     GPIO22 蜂鸣器
GPIO selftest: /dev/gpio2 OK  read=0  ioctl=0     RTC IO0
nsh> uname -a
NuttX 0.0.0 322ad9f1-dirty Sep 20 2026 04:27:31 risc-v esp32p4-function-ev-board
```

**修复了一个 BSP 的真 bug**：`arch/risc-v/src/common/espressif/esp_start.c` 里
`esp_bringup()` 被放在 `nx_start()` **之前**调用。那时调度器没起来，
`register_driver()` 拿 `g_inode_lock` 后无人能释放，永久死锁。开
`CONFIG_DEV_GPIO` 必踩。修法是删掉提前调用，交给板级既有的
`board_late_initialize()`。**这个要告诉 ty**，他后面加任何驱动都会撞上。

**控制台迁移**：UART0（GPIO37/38，需外接 CH340）→ 板载 USB-Serial/JTAG。
参照板级自带的 `configs/usbconsole/defconfig`。一根 USB 线搞定烧录 + NSH。

证据与补丁：

- `app/electric_guard_vision/evidence/openvela-gpio-adaptation-20260920.md`
- `app/electric_guard_vision/evidence/openvela-gpio-selftest-20260920.txt`
- `patches/openvela-p4-gpio-usbconsole.diff`
- `nuttx-overlay/boards/risc-v/esp32p4/esp32p4-function-ev-board/src/esp32p4_guardd.c`

### 3.2 ⚠️ 坏的：`guardd` 起不来（**当前状态**）

`guardd` 是 openvela 侧的执行守护进程，作为 `CONFIG_INIT_ENTRYPOINT` 常驻，
从串口读单字符指令驱动 GPIO。协议：`c`=断闸 `r`=复位 `b`=鸣笛 `s`=查状态。

**它曾经工作过**（连续 3 次复位正常，完整跑过两遍演示），**现在稳定失败**：

```
BRD:1 esp_bringup-done       ← bringup 完成，GPIO 自检三路全 OK
(然后什么都没有)              ← guardd 没有任何输出
```

发 `s` 无回应，发 `b` 写超时（板子那头没在读串口）。

**定位到的位置**：卡在 guardd 打开 `/dev/console` 那一步。同一个位置，之前把
guardd 做成 builtin 应用时，NSH 也是卡在 `nsh_consolemain()`。埋点证据：

```
NX:spawn ret=1          task_spawn 成功
NSH:main-enter          nsh_main 进来了
NSH:before-consolemah   ← 卡在这里
```

**已排除**：不是蜂鸣器（拔掉也一样，3/3 全失败）；不是内存（堆有 297KB 可用，
`HEAP: start=0x4ff7561c romres=0x4ffbfbb0 size=304532`）。

**可疑的时间点**：它是在板子经历了一次**真正的冷上电**（拔插 USB）之后开始
稳定失败的。之前一直是 DTR/RTS 软复位（`rst:0x17 CHIP_USB_UART_RESET`）。

**我改到一半的方案**（未编译未验证，代码已在 WSL 的
`~/nuttx/boards/risc-v/esp32p4/esp32p4-function-ev-board/src/esp32p4_guardd.c`）：
不再自己 `open("/dev/console")`，改用 init 任务已继承的 fd 0/1，并在
`guard_say()` 里加 `ets_printf` 兜底。备份在同目录 `.bak.consoleopen`。
**下一步就是把它编出来烧上验证。**

编译命令（WSL）：

### 3.3 已知缺陷（如实记录，别当成已修复）

**USB-Serial/JTAG 控制台接收侧不稳**：单字符间隔 ≥250ms 输入正常回显，
连续快写会把主机 OUT 端点堵死。`ls` 这类多次小块输出的命令会挂死，
`uname -a` 这类单次输出正常。怀疑是 `esp_usbserial.c` 的 RX FIFO 排空与
OUT 包确认时序问题，未定位。

**`CONFIG_ESPRESSIF_GPIO_IRQ` 关闭，`BOARD_NGPIOINT=0`**：板级与驱动的
中断 API 在 P4 上不匹配（P4 是 `GPIO_INTR0~3`，驱动按单一 `GPIO_INTR_SOURCE` 写）。
断闸是输出通路不依赖中断，本期先关。

## 5. 关键操作手册

### 5.1 烧 openvela

```bash
python -m esptool --chip esp32p4 -p COM3 write_flash --force \
  --flash_size 16MB --flash_mode dio --flash_freq 80m \
  0x2000 D:\openvela\openvela-build\nuttx-guardd-demo.bin
```

- 偏移是 **0x2000**，不是 0x20000
- **不要加 `--baud`** —— USB-Serial/JTAG 上改波特率会让 esptool 崩
- 必须用 `C:\Espressif\tools\python\v5.5.4\venv` 里那个 esptool（4.12.dev3）。
  `D:\Espressif\python_env\idf5.3_py3.11_env` 里的 4.11.0 在 P4 上 stub 会
  Guru Meditation，`--no-stub` 写块会断流

### 5.2 烧 ESP-IDF

```bash
cd D:\openvela\partner\ws-gw\build
python -m esptool --chip esp32p4 -p COM3 write_flash \
  --flash_mode dio --flash_freq 40m --flash_size 16MB \
  0x2000 bootloader\bootloader.bin \
  0x10000 partition_table\partition-table.bin \
  0x20000 electric_guard_p4.bin
```

`0x920000 storage.bin`（4MB）只在第一次或分区表变动时需要，openvela 不会
覆盖到它，日常切换可以省掉。

### 5.3 让 WiFi 连上（**重要，不是自动的**）

板子启动**不会**自动建 esp-hosted transport。队友的设计是：

> 启动阶段跳过 esp-hosted transport 建立（C6 缺席防 SDIO 重试/复位风暴）
> —— WiFi 联机改由连接按钮主动触发

所以必须**在触摸屏上操作**：翻到「链路」页 → SSID 输 `RedmiK60` →
密码输 <热点密码，向队长索取> → 点「连接 WiFi」。

点一次就够，**别连点**（代码里有 2 秒防抖，但会刷日志）。

### 5.4 烧 C6 从机固件（**目前不需要**）

C6 现在工作正常，这一节只是备用。

P4 的 USB-C **够不到 C6**（C6 的 IO9/BOOT 只到 J2 pin6，P4 无 GPIO 接它），
必须用 CH340 接板上 **J2**（2×3 排针）：

| J2 pin | 丝印 | 接 CH340 |
|---|---|---|
| 1 | EN | RST/DTR |
| 3 | TX | RX |
| 4 | GND | GND |
| 5 | RX | TX |
| 6 | BOOT | BT/IO0 |

3V3/5V **不接**（板载已供电）。下载模式：按住 BT → 短按 RST → 松 RST → 松 BT。
先让 P4 停在 bootloader（按住板上 BOOT 短按 RST），避免 P4 驱动 GPIO54 与
下载器 RST 打架。

```bash
esptool.py --chip esp32c6 -p COM4 --baud 115200 \
  --before no_reset --after no_reset write_flash \
  0x0 bootloader.bin 0x8000 partition-table.bin 0x10000 network_adapter.bin
```

注意 C6 的地址体系（0x0/0x8000/0x10000）和 P4 完全不同。
**`ws-c6\build` 里现在只有 bootloader 和分区表，主程序 `network_adapter.bin`
没编，要烧得先 `idf.py set-target esp32c6 && idf.py build`。**

### 6.1 我判断错的（结论已被证伪，别沿着走）

| 我的错误判断 | 实际情况 |

| "C6 从机固件版本不匹配，需要重烧" | **错**。从机 2.12.12 / 主机 2.12.13 只差 patch 号，不校验。C6 一直是好的，只是**没人按过屏上的连接按钮**，SDIO 枚举压根没触发 |

### 6.2 工具链与环境的坑

**openvela 侧**

- **绝不要 `make distclean`** —— 会删掉 `arch/risc-v/src/chip/esp-hal-3rdparty`
  及其中不可再生的本地补丁（PMA/PVT/RTC 关闭等）
- `make olddefconfig` **在这棵树上是坏的**（`nuttx-apps/graphics/lvgl/Kconfig`
  用了 `osource`，解析报错）。改配置用 `/usr/bin/kconfig-tweak` 直接写 `.config`，
  但要自己确认被 `select` 的符号已经是 y
- 从 Git Bash 调 `wsl` 且参数里有 `/mnt/...` 路径时，必须加 `MSYS_NO_PATHCONV=1`，
  否则 MSYS 会把路径转成 Windows 形式导致找不到文件
- 加了新 builtin 应用后，**只改 `.config` 关掉它是无效的**——
  `apps/builtin/builtin_list.h` 不会重新生成，会得到一个假的"对照组"。
  要真正摘掉必须删 `builtin/registry/<name>.bdat/.pdat`、重生成表、
  再从 `libapps.a` 里 `ar d` 掉目标文件。**我就是被这个误导过一轮**
- 在 `apps/examples/` 下新增 builtin 应用会导致 NSH 启动挂死在
  `nsh_consolemain()`，根因未定位。改放板级代码 + 直接作为
  `CONFIG_INIT_ENTRYPOINT` 可绕开 apps/builtin 那条链路

**PowerShell**

- **不支持 `&&`**，用 `;` 连接
- `Out-File -Encoding utf8` **会加 BOM**，写出来的 JSON 用 `json.load` 会报
  `Unexpected UTF-8 BOM`。读的一侧用 `encoding="utf-8-sig"`
- 读串口看中文日志要设 `$port.Encoding = [System.Text.Encoding]::UTF8`，
  否则全是乱码
- 串口同一时刻只能被一个程序占用。串口助手开着 → 烧录失败；网关在跑 →
  串口助手打不开。**录像时反复踩这个**


- `dashboard.html` —— 实时监控面板（`http://127.0.0.1:8765`），数据全部来自

- `scenarios/demo.json` —— 5 条演示事件

### 两条安全约束（**这是设计的核心，别删**）

1. **只能升级，不能降级**。本地判定要断闸就一定断，不管大模型说什么、
   网络通不通。
2. **升级幅度一次最多一级**。实测同一条事件、同一模型、`temperature=0`，
   两次分别给出 ALARM 和 CUT，置信度都是 0.82。**大模型是不确定的，而
   CUT 意味着真停电**。封成单级后，一次幻觉最坏只是多响一次蜂鸣器。

### 大模型的价值在哪（演示剧本第 2 条）

规则引擎只读 `type`/`severity`/`vision_fire`/`vision_smoke` 四个数值，
**不读 `ctx` 那段自由文本**。第 2 条事件（A 相端子 118℃、相邻两相 41/43℃、
温差 75K 持续扩大、电流 9.2A 未过载）所有阈值都不命中，规则判 NONE；
大模型读懂了"不过载却局部高温 = 接触不良 = 电气火灾经典起因"，把结论顶到
告警。**这是语义理解相对阈值判据的真实增量。**

## B. 遗留：内部 DMA 装不下 WiFi + 真实采集

**这是当前最主要的功能性限制，不是配置问题。**

| 场景 | 内部 DMA 剩余 |
|---|---|
| demo mode 开，未联网 | `idma=86620` |
| demo mode 关（ADS8688 SPI + INMP441 I2S 上电） | `idma=22400`，最大连续块 `17396` |
| demo mode 开 + WiFi 已连 | `idma=1168`，最大连续块 `468` |

- C6/esp-hosted 建链需要 **24576 B 连续块** → demo mode 关时拿不出来，
  `[UIS] 内部 DMA 仅剩 16128 B < 24576 B —— 拒绝再发起 SDIO 重试`
- WiFi 起来后内部 DMA 几乎耗尽 → `HTTP_CLIENT: Allocation failed`、
  `esp-tls select() timeout` → IoTDA/MQTT 握手失败

**C6 本身是好的**，这一点已被证伪性测试确认：换成 demo mode 固件后
`[C6-WARMUP] ★ C6 完整枚举成功 OCR=0xa0ffff00`、`H_SDIO_DRV: Card init success`、
`MON: c6=1`，同一块 C6 同一根线。早些时候也曾成功拿到 IP `192.168.17.54`。

**未做的优化方向**（留给接手）：缩小 I2S/SPI 的 DMA 缓冲；或把视觉模块从
云构建里摘掉腾内存；或改用不走 TLS 的上行通道验证链路。

## C. 遗留：MQTT broker 地址过期

`config: broker=mqtt://192.168.71.59:1883`，而板子在 `192.168.17.x`（RedmiK60）。
不同网段，且本机未运行 broker。**华为云 IoTDA 不受影响**，是独立通道。

## D. 遗留：华为云控制台看不到遥测

固件周期调用 `iotda_cloud_publish_telemetry`（main.cpp:2129），但
`iotda_cloud.c` 里明确标注：

> ⚠️ 这 5 个 property 需在 IoTDA 产品模型 telemetry 服务中显式定义后才会入库/显示

**需要在华为云控制台的产品模型里建 `telemetry` 服务**，属性名照抄：

平台对未定义的属性直接丢弃。这是控制台配置项，不是固件缺陷。
