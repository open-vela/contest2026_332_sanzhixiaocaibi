# 电脉卫士 · 演示视频录制脚本

目标时长 **≤ 5 分钟**（大赛硬性要求）。三段分开录，后期拼接。

> **为什么要分段拼接**：本项目是双固件架构。openvela 承载系统底座与断闸
> 执行，ESP-IDF 承载视觉识别、LVGL 界面与华为云上行。一块 ESP32-P4 同一
> 时刻只能跑一个固件，且两者的烧录地址重叠（openvela 在 0x2000，ESP-IDF
> 的 bootloader 也在 0x2000），物理上无法并存。
>
> 这一点在视频开头用一行字幕说明即可，不必回避——**openvela 侧缺少
> MIPI-DSI/CSI 驱动是乐鑫平台的客观现状**，我们把它查证清楚、如实记录，
> 本身就是移植工作的一部分。

| 项 | 值 |

| 串口 | COM3（USB-Serial/JTAG，板子只有这一个口） |
| openvela 固件 | `D:\openvela\openvela-build\nuttx-guardd-demo.bin` |

| esptool | `C:\Espressif\tools\python\v5.5.4\venv\Scripts\python.exe -m esptool` |

**三个坑，先记住**：

1. openvela 烧在 **0x2000**，不是 0x20000
2. **不要加 `--baud`** —— USB-Serial/JTAG 上改波特率会让 esptool 崩
3. 串口同一时刻只能被一个程序占用。串口助手开着的话，烧录会失败

## 一、段① 系统底座 · openvela（约 50 秒）

**烧 NSH 版固件**：

```powershell
python -m esptool --chip esp32p4 -p COM3 write_flash --force `
  --flash_size 16MB --flash_mode dio --flash_freq 80m `
  0x2000 D:\openvela\openvela-build\nuttx-gpio-usbconsole.bin
```

**录屏内容**：串口助手打开 COM3 / 115200，按板子复位键。

画面上会依次出现：

```
*** Booting NuttX ***
...
BRD:12 procfs-done ret=0
GPIO selftest: /dev/gpio0 OK  read=0  ioctl=0     ← GPIO21 三相断闸
GPIO selftest: /dev/gpio1 OK  read=0  ioctl=0     ← GPIO22 蜂鸣器
GPIO selftest: /dev/gpio2 OK  read=0  ioctl=0     ← RTC IO0
BRD:1 esp_bringup-done

NuttShell (NSH)
nsh>
```

然后手敲（**逐字符慢敲，每个字符间隔 ≥250ms**）：

```
uname -a
```

输出：`NuttX 0.0.0 ... risc-v esp32p4-function-ev-board`

**口播要点**：
- 这是 openvela 跑在 ESP32-P4-Function-EV-Board 上
- 三个 GPIO 字符设备是我们本次适配的产物，`ioctl=0` 说明驱动注册、
  VFS 通路、ioctl 全链路打通
- 自检只读不写——`/dev/gpio0` 后面是三相断闸继电器，开机不能主动拉高

> ⚠️ 不要在镜头前敲 `ls`。USB-Serial/JTAG 控制台接收侧有已知缺陷，
> `ls` 这类多次小块输出的命令会挂死（已记录在 evidence/）。`uname -a`
> 这类单次输出是正常的。

## 二、段② AI 辅助断闸决策 · openvela（约 2 分钟，**主段**）

**烧 guardd 固件**：

```powershell
python -m esptool --chip esp32p4 -p COM3 write_flash --force `
  --flash_size 16MB --flash_mode dio --flash_freq 80m `
  0x2000 D:\openvela\openvela-build\nuttx-guardd-demo.bin
```

**关掉串口助手**（不然网关抢不到 COM3），然后：

```powershell
cd D:\openvela\vela-ws\contest2026_332_sanzhixiaocaibi\tools
C:\Espressif\tools\python\v5.5.4\venv\Scripts\python.exe guard_bridge.py `
  --port COM3 --scenario scenarios\demo.json --pace 5
```

浏览器打开 `http://127.0.0.1:8765`，**全屏**（1600×900 以上走三栏布局）。

**构图**：左边面板全屏，右边板子实物，同一个画面。

**五条事件依次走**：

| # | 事件 | 本地规则 | 大模型 | 最终 | 画面 |
|---|---|---|---|---|---|
| 1 | OVERVOLT Lv1 | NONE | NONE | NONE | 绿色，无动作 |
| 2 | **TEMP 端子 118℃ / 温差 75K** | NONE | CUT | **ALARM** | **大模型那一行高亮＋"升级"标** |
| 3 | OVERLOAD Lv2，烟雾 0.31 | ALARM | ALARM | ALARM | 黄色，板子鸣响 |
| 4 | **ARC Lv2 + 火情 0.71** | **CUT** | CUT | **CUT** | **整页转红，断闸灯"已断开"** |
| 5 | TEMP Lv1，断闸后回落 | NONE | NONE | NONE | 恢复绿色 |

### 第 2 条：讲大模型凭什么值这个钱（**必须讲**）

这条是回答"大模型在哪体现"的。画面上大模型那一行会变琥珀色并弹出
"升级"标签。

> 这条事件里，故障等级 Lv1、火情 0.08、烟雾 0.11——**所有数值阈值全部
> 不命中**，规则引擎判"无需动作"。
>
> 但大模型判了断闸。它读的是规则引擎根本不看的那段现场描述：A 相端子
> 118℃，相邻两相只有 41℃ 和 43℃，温差 75K 还在持续扩大，而电流 9.2A
> 远低于额定值。**不过载却局部高温，这是接触不良、端子松动的典型特征，
> 是电气火灾最经典的起因之一。** 阈值判据看不见这个组合，语义理解能。
>
> 但我们没有直接采纳它的断闸建议。最终动作是告警。

### 第 2 条还要讲：为什么不敢全听它的

> 我们实测过：同一条事件、同一个模型、temperature 设成 0，两次运行分别
> 给出 ALARM 和 CUT，置信度都是 0.82。**大模型本身就是不确定的，而断闸
> 意味着真停电。**
>
> 所以我们加了第二道约束：升级幅度一次最多一级。本地判 NONE 时，模型
> 就算喊 CUT 也只能升到 ALARM。这样一次幻觉最坏只是多响一次蜂鸣器，
> 不会让配电柜无故拉闸。

### 第 4 条：讲交叉验证（高潮）

> 单看电气特征，这只是 Lv2，按规则不断闸。单看视觉，火焰识别也可能误报。
> 但两路**独立**证据同时成立——电弧的 2.1kHz 谐波超阈，加上 YCbCr 火焰
> 判据连续 9 帧命中且面积持续增长——交叉验证后升级为断闸。

### 贯穿全段的安全设计

> 判断端在主机，执行端在 openvela。但本地规则引擎保留否决权：大模型
> 只能升级、不能降级，且一次最多升一级。本地判定要断闸就一定断，不管
> 大模型说什么、网络通不通。一个安全装置不能把最终否决权交给一条会
> 超时的链路。

**面板上的数据全是真的**：两盏指示灯来自板子自报的 `GUARD STATUS
cut=1 buzzer=0`，每次动作后网关都会补发 `s` 重新读一次。

> 顺带说明 openvela 为什么不直接接大模型：P4 没有射频，要借板载 C6 的
> WiFi；而 openvela 的 `ESPRESSIF_WIFI` Kconfig 依赖里只有 C3 和 C6，
> **P4 不在列表里**，且树中没有 esp-hosted 驱动。这是我们查证后的结论。

## 三、段③ 视觉识别与云上行 · ESP-IDF（约 1 分 40 秒）

**烧回视觉固件**（四个镜像，注意偏移）：

```powershell
cd D:\openvela\partner\ws-gw\build
python -m esptool --chip esp32p4 -p COM3 write_flash `
  --flash_mode dio --flash_freq 40m --flash_size 16MB `
  0x2000   bootloader\bootloader.bin `
  0x10000  partition_table\partition-table.bin `
  0x20000  electric_guard_p4.bin `
  0x920000 storage.bin
```

**录屏内容**：

1. MIPI 屏上的 LVGL 界面（实时波形、故障等级、视觉页）
2. 摄像头对着火源/火焰视频，视觉页上火情置信度跳起来
3. 华为云 IoTDA 控制台上看到设备上行的遥测数据
4. 云端下发一条命令，板子响应（`on_iotda_cmd` 通道）

**口播要点**：
- 视觉走 YCbCr 火焰判据 + AVT 面积时序分析，纯 CPU 实现，不依赖 NPU
- 华为云 IoTDA 与本地 MQTT broker 双通道并行，互不影响
- 这一段跑在 ESP-IDF 上，因为 openvela 目前没有 MIPI-CSI/DSI 驱动

## 五、录砸了的补救

| 现象 | 原因 | 处理 |
|---|---|---|
| esptool 连不上 | 串口被串口助手/网关占着 | 关掉占用的程序 |
| 烧完不启动 | 偏移写成 0x20000 了 | 重烧 0x2000 |
| esptool 报 Guru Meditation | 加了 `--baud` | 去掉 |
| NSH 敲命令没反应 | 敲太快 | 逐字符，间隔 ≥250ms |
| 面板显示"网关未运行" | guard_bridge.py 退出了 | 重新跑 |
| 面板三栏挤成一栏 | 窗口宽度 < 1180px | 全屏或调大窗口 |
